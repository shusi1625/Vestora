## 백엔드 계측: 로컬 범위

[local-spans.ts](../../backend/src/api/local-spans.ts)는 `LOCAL_API_SPANS=true`일 때만 활성화된다. 요청 ID별 lifecycle, freshness RPC, snapshot 진입·callback·domain, query, metrics hit/new/join을 기록하며 기본값은 비활성이다. [sync-context.ts](../../backend/src/api/sync-context.ts), [app.ts](../../backend/src/app.ts), [설명과 격리 테스트](../../backend/README.md)에 구현 근거가 있다.

과거 로컬 기록은 응답 JSON·조회 순서·repeatable-read snapshot·timeout·RPC/cache 정책 유지와 Fastify.inject/fake DB/RPC의 off/on 비교를 다룬다. 현재 소스 두 모드를 비교한 것이며 이전 릴리스 동등성, 실제 DB pool 대기·RPC retry/cache, 실제 socket abort, 배포판 병목이나 비용 감소를 증명하지 않는다. span은 중첩·병렬 구간을 포함하므로 합산하지 않고 서버·클라이언트 시각을 직접 차감하지 않는다. 요청 ID 헤더의 CORS exposed headers 추가도 포함하지 않는다.

로컬 소스에서 API snapshot 전에 최신 블록 RPC를 기다리는 경로는 후속 계측 후보다. 배포 백엔드에는 이번 로컬 span이 없으므로 G2/G3의 지연을 RPC/DB/직렬화 중 하나의 원인으로 확정할 수 없다.

| `dbsurplus` | 09:16:13.791 | 09:06:00.000 | 613.791초 | 480초 | 0 |

**613.791초 > 480초**로 133.791초 초과했다. 검사 순서상 dbcredits에서 먼저 거부됐고 dbsurplus도 같은 나이라는 점은 별도 산술 대조다. 마지막 AWS 명령 자체는 성공했다. CPU credit 고갈, CPU 자원 고갈 또는 AWS 인증 실패가 확인된 것이 아니다. 표본 신선도를 확인하지 못해 중단한 결과다.

직전 snapshot의 최신 credit 표본은 09:10Z였으나 마지막 응답에서는 09:06Z로 후퇴했다. 조회창 정렬·300초 주기 지표·발행 지연을 후속 조사할 필요가 있지만 원문만으로 내부 원인을 확정할 수 없다. 기준 480초를 늘려 통과 처리하지 않았다.

실제 측정 구간 안의 timestamp만 고르고 반복 표본을 제거한 별도 감사에서는 API CPU 최대 약 4.30%, indexer CPU 약 4.50%, DB CPU 약 5.50%, DB 연결 5, credits 288/surplus 0을 기록했다. 운영 응답 30회는 모두 applied, DB ok, lag 0~2였다. 이 유계 관측은 마지막 신선도 실패를 취소하거나 모든 순간·중단 이후의 가용성을 보장하지 않는다.

예약·전송·완료는 각각 230개로 일치했고 rolling 1초 시작 최대 5, 동시 요청 최대 4, 종료 시 잔여 0이었다. stop 이후 신규 API 전송·AWS 명령은 없었다. AWS CLI 63회는 preflight 8 + refresh 11×5이며 모두 읽기 명령으로 성공했다. 오프라인 감사의 36개 검증 성공은 원문 대조와 예상된 guard 거부를 확인한 것이며 G3 실행 성공이 아니다.

### 실행 범위와 보존

앞선 별도 discovery 2회는 합계 6 GET/16 AWS 읽기 CLI였고 G3 본 실행 230 GET/63 CLI와 구분한다. 이 후속 범위의 합계 236 GET/79 CLI를 G3 성능 표본 수로 사용하지 않는다.

모의 리허설은 실제 API/AWS 호출 없이 격리했고 실제 실행과 섞지 않았다. 실제 gateway·임시 preview는 종료했으며 기존 fixture의 요청 cap 초기화·증가·재시작은 하지 않았다. 과거 특정 시점의 fixture 프로세스 생존을 현재 상태로 보장하지 않는다.

감사한 실행기의 범위에 지갑 서명·신규 체인 거래·배포·AWS mutation·직접 공용 RPC 부하·pending 기록 초기화는 없다. 이 구분은 실행기 경로·읽기 명령·원문 대조에 근거하며 시스템 전체에 대한 독립 카운터가 있는 것처럼 쓰지 않는다. API/backend/indexer 내부의 정상 RPC 읽기나 실제 청구 비용은 0이라고 측정한 것이 아니다.
